## 2. 架构设计

### 2.1 现状

```
lib/
├─ main.dart              737 行：App + 列表页 + 全部业务逻辑
├─ services/             SmsRepository / sms_filter / csv_exporter（纯函数）
├─ widgets/message_item.dart
└─ l10n/                 ARB + generated
```

`services` 层抽得很干净（纯函数 + 无 Flutter 依赖，可单测），`MessageItem` 也已抽出。**问题集中在 `_SmsHomePageState`**：它同时承担权限申请、默认应用管理、查询、三种过滤、单条/批量删除、CSV 导出、全部 UI 构建，且用 `ValueNotifier` 手工管理加载态。

### 2.2 结构性问题

- **A1｜God State**：`_SmsHomePageState` 约 660 行、20+ 职责。新增一个过滤维度就要在这个类里再塞状态 + 查询分支 + UI 按钮。
- **A2｜AGENTS.md 的规则在反向固化问题**：`lib/main.dart` 的注释 "Keep UI in lib/main.dart" 是明确指令。它保护了"小项目不要过度分层"，但也让 UI 拆分永远停在"抽出一个 MessageItem"。建议改为"按 feature 组织：`sms_list/`（controller + page + widgets），services 保持纯逻辑"。
- **A3｜index 作为跨组件契约**：`MessageItem` 的 `onDelete/onRemove/onSameAddress/onSameSim` 全部按 `int index` 回调。index 在异步间隙会漂移——CHANGELOG 里已经为此修过多次（"不再按 index 回查实时列表"）。这是**用补丁掩盖设计问题**：应改为按 `id`（或对象引用）定位。
- **A4｜样板三分重复**：`_querySms`（130-162）、`_sameAddress`（202-227）、`_sameSim`（229-256）是同一套"权限检查 → loading → try/catch → 排序 → `_setFullList`"模板，约 60 行可合并为一个 `_runQuery(Future<List<SmsMessage>> Function())`。
- **A5｜ValueNotifier 可变更新**：`main.dart:168-169` 先 `_showList.value.removeAt(index)` 原地改，再 `_showList.value = [..._showList.value]` 触发通知——先污染再复制的反模式，建议统一为不可变更新。
- **A6｜无 repository 接口**：`SmsRepository` 是具体类，替换 `sms_advanced` 时无法在测试里注入 mock，也无法并行灰度新旧实现。

## 3. 性能表现

| # | 位置 | 问题 | 量级估计 |
| --- | --- | --- | --- |
| **P1** | `main.dart:379-396` 批量删除 | 逐条 `await removeSmsById(id, threadId)`，每条一次 MethodChannel 往返（插件内部 `invokeMethod('removeSms')`，一次 `ContentResolver.delete`）。3000 条 = 3000 次跨进程调用，串行执行，无进度、无取消、无超时 | 千条级可达分钟级；期间 UI 只有一个 loading 遮罩 |
| **P2** | `sms_repository.dart:13` + 插件 `getAllSms` | 插件 `getAllSms` = `querySms(kinds: [Sent, Inbox, Draft])`，**3 次独立查询**，合并后再排序（`sort = true`）后再在 Dart 侧重新降序排。全部短信经 JSON 编解码一次性跨通道回传主线程 | 2 万条短信 ≈ 数 MB 内存峰值 + 主线程 JSON 解码卡顿；还多做了两次全量排序 |
| **P3** | `main.dart:474-484` CSV 导出 | `buildSmsCsv` 一次性构造全量字符串，再 `utf8.encode` 成第二份全量字节（注释已说明有意不改流式） | 万条短信 ≈ 两份数 MB 常驻内存 |
| **P4** | `main.dart:84-87` `_setFullList` | 每次查询都新建 `GlobalKey` → 整个 AnimatedList 子树丢弃重建 | 每次查询一次全量重建，但列表本身是 lazy 的，影响可接受 |
| **P5** | `sms_filter.dart:47-48` | `sortByDateDesc` 在比较器内每次 `DateTime.fromMillisecondsSinceEpoch(0)` 新建对象 | 万条排序 ≈ 数十万次临时对象；应提为 `static final` |

补充说明：插件 `removeSmsById` 内部 `catch (e) { print(e); }` 吞掉异常返回 `null`，因此 `main.dart` 里的 `try/catch` 在删除路径上基本是死代码——失败实际走 `ok != true` 分支。逻辑结果正确，但 `print(e)` 会污染日志。

## 4. 依赖管理

### 4.1 `sms_advanced ^1.1.0` —— 最大技术债

已核对 pub.dev / 镜像数据：

- 最后发布 2023-06，**近 2 年无新版本**；GitHub 近 52 周 **0 commit**，37+ open issue，日下载量约 6。
- 自带 Kotlin Gradle Plugin，未来 Flutter 版本将拒绝构建（AGENTS.md 已记录）。
- 不支持 SQL 下推过滤、不支持批量删除、不支持分页式流式返回——**本项目 3.1 的性能瓶颈全部由它造成**。
- 一旦 Flutter/AGP 再升一档，现有 `compileSdk=37` 硬编码 + lint 禁用 + namespace 回填三件套可能同时失效。

### 4.2 其他依赖问题

- **D1｜未使用的直接依赖**：`cross_file: ^0.3.5+5` 在 `lib/` 下**没有任何 import**（`XFile` 由 `share_plus` 转出）。全仓库仅 `pubspec.yaml:41` 一处引用 → 可删，或显式 import 后再保留。
- **D2｜无自动依赖更新**：没有 `.github/dependabot.yml`，全靠手动 `flutter pub upgrade`。
- **D3｜Actions 仅 tag 固定**：`actions/checkout@v7.0.1` 这类 tag 可被上游移动，严格供应链加固应 SHA 固定。
- **D4｜符号表未归档**：`distribute_options.yaml` 已开 `obfuscate` + `split-debug-info: build/symbols/apk`，但产物只上传 `dist/**`，符号表不随 Release 发布 → **线上崩溃栈将无法还原**。
- **D5｜工具型 dev 依赖缺说明**：`flutter_launcher_icons` / `flutter_native_splash` 有配置文件但 README 未写如何执行。

依赖本身版本较新（permission_handler 13 / share_plus 13 / csv 8 / flutter_lints 6），`pubspec.lock` 已入库，`environment: sdk: ^3.13.4` 合理。

## 5. 错误处理与健壮性（本项目最强项）

做得好的：

- `isDefaultSmsApp()` 三态 + fail-safe：拿不到身份就拦截删除，绝不误判为"不是默认"。
- 查询路径三处统一 try/catch + `finally` 复位 loading。
- 导出拆成"保存"与"分享"两阶段分别捕获，提示语义区分（`toast_save_failed` vs `operation_failed`）。
- 批量删除按快照执行 + 失败计数，不再中途崩溃。
- 导出后只删本次 CSV，不递归清临时目录。

仍有缝隙：

- **E1｜静默失败**：`_setDefaultApp`（439-449）中 `set` 返回 `"no"`（已发起系统确认流程）且 `get` 不等于本包名时，**什么都不提示**。用户点"设为默认短信应用"后：系统弹窗确认了 → 无提示；取消了 → 也无提示。同理 `_resetDefaultSmsApp` 成功时无正向反馈。
- **E2｜删除 try/catch 实际不可达**（见 3.1 插件吞异常）——建议改为显式判定 `ok != true` 并区分 `null`（异常）与 `false`（拒绝）。
- **E3｜无并发守卫**：`_querySms` 可被连续触发（快速点"全部"/日期/搜索），慢的旧请求返回后会覆盖新结果；无请求 token 或序号。
- **E4｜批量删除无中断**：一旦开始只能等完，无法取消；>3000 条的提示 toast（`main.dart:371-373`）紧接着被 `_showLoading.value = true` 的遮罩盖住，几乎看不到。
- **E5｜无崩溃上报**：考虑到隐私定位（不上网）这是合理取舍，但意味着线上问题只能靠用户主动反馈。

## 9. 头脑风暴：优化方向

### 9.1 架构与工程（治本）

1. **引入列表控制器**：把 `_SmsHomePageState` 拆成 `SmsListController`（ChangeNotifier 或 Riverpod `AsyncNotifier`）+ 纯展示 Page + widgets，同步修订 AGENTS.md 的"UI 全放 main.dart"规则。收益：新增过滤维度/多选删除不再触碰 700 行巨类；controller 可脱离 widget 单测。
2. **仓储接口化**：`abstract class SmsRepository`，运行时注入实现。收益：为替换 `sms_advanced` 铺路 + 测试可 mock。
3. **自建 platform channel 替换 `sms_advanced`**（战略级）：Kotlin 侧用 `ContentResolver` 实现分页查询（`start/count`）、SQL selection 下推（日期/关键词/号码/SIM 全部在 SQL 层过滤）、`ContentProviderOperation` 批量删除、`EventChannel` 回传进度。收益：一次性解决 P1/P2 性能问题、解除 AGP/Flutter 升级锁死、去掉 root `build.gradle.kts` 里的 namespace 回填与 lint 禁用三件套。
4. **把 index 契约换成 id 契约**：`MessageItem` 回调传 `SmsMessage` 或 `id`。收益：消灭一整类"异步间隙索引漂移"bug，已有补丁可全部简化。
5. **工程流水线加固**：CI 加格式门禁、`lefthook` 本地钩子、覆盖率门槛（先 40% 再抬）、符号表随 Release 上传、Dependabot。

### 9.2 性能与体验（用户可感知）

6. **批量删除改造**：原生批量 `delete ... WHERE _id IN (...)`，Dart 侧显示"已删除 i/n"进度并提供取消。收益：3000 条从分钟级降到秒级。
7. **分页 / 增量加载**：先加载最近 200 条，滚动加载更多；过滤条件全部下推。收益：冷启动与内存大幅下降。
8. **关键词搜索防抖 + 本地过滤**：已有全量数据时不再重新查库，直接在 Dart 侧过滤（配合 7 后收益有限，但短期见效快）。
9. **CSV 流式写盘 + UTF-8 BOM**：`IOSink` 逐行写，`\uFEFF` 开头。收益：内存峰值下降；Excel 直接双击不乱码（替代"请用 UTF-8 打开"的提示）。
10. **CSV 字段规范化**：`kind`/`state` 输出 `received`/`none` 等规范值而非 `SmsMessageKind.Received`；`date` 输出 ISO-8601 或毫秒时间戳。收益：导出文件可被 Excel/数据库直接分析。
11. **修复"恢复默认短信应用"**：Android 10+ 改为跳转 `Settings.ACTION_MANAGE_DEFAULT_APPS_SETTINGS`（或 Role 设置页），并补齐 `<queries>`。收益：修复一个目前基本无效的核心功能。

### 9.3 功能扩展（增长）

12. **多选删除**：列表项加复选框 + "删除选中"。当前只能"删除当前列表全部"，是最大的功能缺口（用户必须靠过滤间接表达选择）。
13. **按号码聚合统计视图**：按号码/发送方统计条数、时间跨度，让用户知道"该删谁"。这是同类工具的高频诉求。
14. **删除前自动备份**：批量删除前提示"先导出 CSV 备份"，一键完成。
15. **引导流程**：空状态现在是三个并列按钮，改为"① 授予权限 → ② 设为默认 → ③ 开始清理"的分步引导，降低新用户流失。
16. **规则化清理**：保存常用清理规则（如"删除 3 个月前的所有验证码短信"），支持一键复用。
17. **本地化增强**：`num_sms`/`delete_num` 改用 ARB ICU plural；日期用 `DateFormat` 按 locale 格式化；补 RTL 与大字体缩放适配、Semantics 标签。
